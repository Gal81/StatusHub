## 5.1. Разбор текущего кода

**Что изучаем.** Разделение ответственности: какие «роли» сейчас смешаны
в `index.ts` (HTTP, валидация, бизнес-логика, конфигурация, запуск).

**Задание.**

1. Прочитать `server/src/index.ts` и отметить комментариями, к какой роли
   относится каждый фрагмент.
2. Ответить: что будет сложно сделать с текущим кодом? (Протестировать
   проверку сайта без HTTP? Переиспользовать её для автопроверок в этапе 7?)
3. Составить план разделения и согласовать с наставником.

**Критерии готовности.**

- Есть письменный план: какие модули появятся и какую проблему решает каждый.

**Вопросы для самопроверки.**

- Что такое «ответственность» модуля?
- Какие изменения в будущих этапах затронут проверку сайта, а какие — HTTP?

**Документация.**

- [Wikipedia: Separation of concerns](https://en.wikipedia.org/wiki/Separation_of_concerns)

## 5.2. Сервисный слой: логика проверки

**Что изучаем.** Бизнес-логика не должна знать про HTTP-фреймворк. Функция
проверки принимает URL и настройки, возвращает результат — её можно вызвать
из маршрута, из таймера, из теста.

**Задание.**

1. Вынести проверку сайта в `server/src/services/checker.ts`.
2. Функция не импортирует ничего из Fastify и не работает с `request`/`reply`.
3. Таймаут передаётся параметром, а не берётся из глобальной константы.
4. Маршрут только принимает запрос, вызывает сервис и отдаёт ответ.

**Критерии готовности.**

- Поведение API не изменилось (проверить теми же запросами, что в этапе 3).
- `checker.ts` можно вызвать из playground-скрипта без запуска сервера.

**Вопросы для самопроверки.**

- Почему сервис не должен знать про `reply`?
- Чем передача таймаута параметром лучше глобальной константы?

## 5.3. Маршруты как плагины Fastify

**Что изучаем.** Плагины — способ Fastify разбивать приложение на части:
`app.register`, префиксы, инкапсуляция.

**Задание.**

1. Вынести маршруты в `server/src/routes/health.ts` и `server/src/routes/check.ts`
   как плагины.
2. Зарегистрировать их с префиксом `/api`.
3. Разобрать, что такое инкапсуляция в Fastify и где она проявится.

**Критерии готовности.**

- API работает как прежде, `index.ts` стал коротким.

**Вопросы для самопроверки.**

- Что делает `app.register`, и почему он асинхронный?
- Зачем префикс задавать при регистрации, а не в каждом маршруте?

**Документация.**

- [Fastify: Plugins](https://fastify.dev/docs/latest/Reference/Plugins/)

## 5.4. Конфигурация

**Что изучаем.** Конфигурация в одном месте: все переменные окружения
читаются и проверяются при старте, остальной код получает готовый
типизированный объект.

**Задание.**

1. Создать `server/src/config.ts`, который читает и проверяет `PORT`, `HOST`,
   таймаут проверки.
2. Нигде, кроме `config.ts`, не обращаться к `process.env`.
3. При некорректной конфигурации сервер не стартует и сообщает, что не так.

**Критерии готовности.**

- `process.env` встречается только в `config.ts`.

**Вопросы для самопроверки.**

- Почему лучше упасть при старте, чем во время обработки запроса?
- Как этот подход упростит тесты и деплой?

## 5.5. Создание приложения отдельно от запуска

**Что изучаем.** Разделение «собрать приложение» (`buildApp()`) и «запустить
его на порту» (`listen`). Это позволяет тестировать приложение без реального
сервера (этап 8).

**Задание.**

1. Создать `server/src/app.ts` с функцией `buildApp(config)`.
2. `index.ts` только читает конфигурацию, вызывает `buildApp` и `listen`.
3. Нарисовать (текстом или схемой) зависимости между модулями и проверить,
   что нет циклических зависимостей.

**Критерии готовности.**

- Структура `server/src` описана в README.
- Можете объяснить, какой модуль от какого зависит и почему.

**Вопросы для самопроверки.**

- Зачем разделять создание приложения и запуск?
- Что такое циклическая зависимость модулей, и чем она плоха?

**Документация.**

- [Fastify: Testing — Separating concerns](https://fastify.dev/docs/latest/Guides/Testing/)

## 3.1. Как устроен HTTP

**Что изучаем.** HTTP — текстовый протокол «запрос — ответ». Запрос: метод,
путь, заголовки, тело. Ответ: статус, заголовки, тело. Методы GET и POST, их
смысл. Группы статусов (2xx, 3xx, 4xx, 5xx). HTTPS — тот же HTTP поверх
зашифрованного соединения (TLS).

**Задание.**

1. Выполнить `curl -v https://example.com` и разобрать каждую строку вывода:
   что отправил клиент, что вернул сервер.
2. Выполнить `curl -v http://127.0.0.1:3000/health` для нашего сервера.
3. Найти сайт, который отвечает редиректом (3xx), и посмотреть заголовок `Location`.
4. Открыть DevTools → Network в браузере на любом сайте и найти те же части
   запроса и ответа.

**Критерии готовности.**

- Можете показать в выводе `curl` метод, путь, статус, заголовки и тело.

**Вопросы для самопроверки.**

- Чем GET отличается от POST по смыслу и по устройству запроса?
- Чем 401 отличается от 403, 404 от 410, 500 от 503?
- Что защищает HTTPS, а что нет?
- Зачем заголовок `Content-Type`?

**Документация.**

- [MDN: Overview of HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Overview)
- [MDN: HTTP request methods](https://developer.mozilla.org/en-US/docs/Web/HTTP/Methods)
- [MDN: HTTP response status codes](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status)

## 3.3. POST и тело запроса

**Что изучаем.** Как клиент передаёт данные серверу: тело запроса в JSON и
заголовок `Content-Type: application/json`. Как Fastify разбирает тело.
Типизация тела через generic-параметр маршрута.

**Задание.**

1. Создать `POST /api/check`, который пока просто возвращает полученный URL.
2. Типизировать тело через generic маршрута, используя тип из `types.ts`.
3. Отправить запрос через `curl` с `-H 'Content-Type: application/json'` и `-d`.
4. Отправить запрос без заголовка, с пустым телом, с невалидным JSON —
   разобрать ответы.

**Критерии готовности.**

- Корректный запрос возвращает отправленный URL.
- Поведение для некорректных запросов разобрано и записано.

**Вопросы для самопроверки.**

- Почему проверка URL — POST, а не GET с query-параметром? Какие есть доводы за оба варианта?
- Проверяет ли generic `{ Body: ... }` данные во время выполнения?
- Что произойдёт, если клиент пришлёт `{"url": 123}`?

**Документация.**

- [Fastify: TypeScript — Using Generics](https://fastify.dev/docs/latest/Reference/TypeScript/#using-generics)

## 3.4. Валидация входящих данных

**Что изучаем.** Типы TypeScript не существуют во время выполнения, поэтому
входящие данные нужно проверять. В Fastify для этого есть JSON Schema:
описываем схему тела, и некорректные запросы получают `400` автоматически.
Дополнительная проверка смысла (URL только `http`/`https`).

**Задание.**

1. Описать JSON Schema для тела `POST /api/check`: объект с обязательным
   строковым полем `url`, без лишних полей.
2. Подключить схему к маршруту и проверить ответы на некорректные запросы.
3. Добавить проверку, что URL корректный и использует `http:` или `https:`
   (функция из этапа 1). Для неподходящего URL — ответ `400` с понятным сообщением.
4. Обсудить с наставником: чем опасен сервис, который делает запросы на
   любой URL от пользователя (SSRF). Подробно — в этапе 9.

**Критерии готовности.**

- `{}`, `{"url": 123}`, `{"url": "ftp://x"}`, `{"url": "abc"}` получают `400`.
- Корректный URL проходит.

**Вопросы для самопроверки.**

- Почему недостаточно TypeScript-типов для тела запроса?
- Чем валидация формы данных (схема) отличается от проверки смысла (бизнес-правила)?
- Что такое SSRF, и почему он актуален именно для StatusHub?

**Документация.**

- [Fastify: Validation and Serialization](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)
- [JSON Schema: Getting Started](https://json-schema.org/learn/getting-started-step-by-step)

## 3.5. Проверка доступности сайта

**Что изучаем.** Как сервер сам выступает HTTP-клиентом: `fetch` из Node.js.
Что считать «сайт доступен». Измерение времени ответа. Редиректы. Методы
`HEAD` и `GET` для проверки — плюсы и минусы.

**Задание.**

1. В `POST /api/check` выполнить запрос к переданному URL и вернуть:
   доступен ли сайт, HTTP-статус, время ответа.
2. Использовать результат в виде discriminated union из `types.ts`.
3. Решить и записать в коде комментарием: какие статусы считаем «доступен».
4. Разобрать, как `fetch` обрабатывает редиректы по умолчанию и какое время
   мы измеряем.

**Критерии готовности.**

- Проверка работает для рабочего сайта, страницы 404 и сайта с редиректом.

**Вопросы для самопроверки.**

- Если сайт вернул `500`, он «доступен»? А `404`? Обоснуйте своё решение.
- Что именно измеряет наше время ответа: до заголовков или до конца тела?
- Почему некоторые сайты по-разному отвечают на `HEAD` и `GET`?

**Документация.**

## 3.6. Таймауты и сетевые ошибки

**Что изучаем.** Сетевые запросы могут зависнуть или упасть: несуществующий
домен (DNS), отказ в соединении, обрыв, медленный сервер. Ограничение времени
через `AbortSignal.timeout()`. Как отличать «сайт недоступен» от «ошибка нашего API».

**Задание.**

1. Добавить таймаут проверки (например, 10 секунд).
2. Проверить сценарии: несуществующий домен, закрытый порт
   (`http://127.0.0.1:9`), очень медленный ответ (можно сделать свой
   «медленный» маршрут на сервере для теста).
3. Для каждого сценария вернуть понятный результат проверки, а не `500`.
4. Посмотреть, что лежит в объекте ошибки (`error.name`, `error.cause`).

**Критерии готовности.**

- Ни один из сценариев не приводит к падению сервера или ответу `500`.
- Результат различает таймаут и другие сетевые ошибки.

**Вопросы для самопроверки.**

- Почему недоступность проверяемого сайта — это успешный ответ нашего API?
- Что произойдёт без таймаута, если сайт никогда не ответит?
- Как ошибка `fetch` отличается от ответа с кодом 5xx?

**Документация.**

- [MDN: AbortSignal.timeout()](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/timeout_static)
- [MDN: fetch() — exceptions](https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch#exceptions)

## 3.7. Обработка ошибок и формат ответов API

**Что изучаем.** Единый формат ошибок API, чтобы клиенту было легко их
обрабатывать. Как Fastify обрабатывает брошенные ошибки, `setErrorHandler`,
`setNotFoundHandler`. Принципы REST: ресурсы, методы, статусы.

**Задание.**

1. Определить единый формат ответа с ошибкой и описать его типом.
2. Настроить обработчики ошибок и 404 так, чтобы все ошибки шли в этом формате.
3. Убедиться, что внутренние детали (стек вызовов) не уходят клиенту.
4. Описать API в README: маршруты, примеры запросов и ответов.

**Критерии готовности.**

- Ошибки валидации, 404 и непредвиденные ошибки возвращаются в одном формате.
- В README есть описание API.

**Вопросы для самопроверки.**

- Почему нельзя отдавать клиенту стек ошибки?
- Что такое REST, и насколько наш API ему соответствует?
- Какой статус вернуть, если наш сервер упал из-за бага? А если клиент прислал мусор?

**Документация.**

- [Fastify: Errors](https://fastify.dev/docs/latest/Reference/Errors/)

## 6.1. Зачем нужна база данных

**Что изучаем.** Сейчас данные живут в памяти и пропадают при перезапуске.
Почему JSON-файл (этап 2) плохо масштабируется: одновременная запись, поиск,
целостность. Что даёт СУБД: транзакции, запросы, ограничения.

**Задание.** Сформулировать письменно требования к хранению данных StatusHub:
какие данные, какие операции, какие запросы будут частыми.

**Критерии готовности.** Есть список требований, согласованный с наставником.

**Вопросы для самопроверки.**

- Какие проблемы JSON-файла решает база данных?
- Что такое транзакция?

## 6.2. PostgreSQL и основы SQL

**Что изучаем.** Установка PostgreSQL локально, клиент `psql`. Базовый SQL:
`CREATE TABLE`, `INSERT`, `SELECT`, `WHERE`, `ORDER BY`, `UPDATE`, `DELETE`.

**Задание.** Установить PostgreSQL, создать учебную БД и руками в `psql`
выполнить все базовые операции на тестовой таблице.

**Критерии готовности.** Можете без подсказок написать запросы на создание,
чтение, изменение и удаление строк.

**Вопросы для самопроверки.**

- Чем `DELETE` без `WHERE` опасен?
- Что такое первичный ключ?

**Документация.**

- [PostgreSQL Tutorial](https://www.postgresql.org/docs/current/tutorial.html)

## 6.3. Модель данных: таблицы и связи

**Что изучаем.** Реляционная модель: таблицы `sites` и `checks`, связь
«один ко многим», внешний ключ, `ON DELETE CASCADE`, ограничения
(`NOT NULL`, `UNIQUE`), типы колонок, `JOIN`.

**Задание.** Спроектировать таблицы, создать их в `psql`, наполнить тестовыми
данными, написать запрос «сайты с последней проверкой».

**Критерии готовности.** Схема обоснована: можно объяснить тип и ограничения
каждой колонки.

**Вопросы для самопроверки.**

- Почему результаты проверок — отдельная таблица, а не поле в `sites`?
- Что произойдёт с проверками при удалении сайта, и почему?

**Документация.**

- [PostgreSQL: Foreign Keys](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK)
- [PostgreSQL: Joins Between Tables](https://www.postgresql.org/docs/current/tutorial-join.html)

## 6.4. Выбор инструмента и подключение из Node.js

**Что изучаем.** Варианты работы с БД из Node.js: драйвер с SQL-запросами,
query builder, ORM — плюсы и минусы каждого. Пул соединений.
Параметризованные запросы и SQL-инъекции.

**Задание.**

1. Сравнить варианты с наставником и выбрать инструмент (для обучения
   рекомендуется начать с драйвера и чистого SQL — так видно, что происходит).
2. Подключиться к БД, строка подключения — через `config.ts`.
3. Показать на примере, как конкатенация строк приводит к SQL-инъекции, и как
   параметры её предотвращают.

**Критерии готовности.** Сервер подключается к БД при старте и выполняет
тестовый запрос.

**Вопросы для самопроверки.**

- Что такое SQL-инъекция?
- Зачем нужен пул соединений?

**Документация.**

- [node-postgres](https://node-postgres.com/)
- [OWASP: SQL Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)

## 6.5. Миграции

**Что изучаем.** Миграции — версионируемые изменения схемы БД, которые
хранятся в репозитории и применяются одинаково у всех разработчиков и на сервере.

**Задание.** Оформить создание таблиц как миграции и научиться применять их
на чистой БД.

**Критерии готовности.** Чистая БД получает актуальную схему одной командой.

**Вопросы для самопроверки.**

- Почему нельзя просто менять схему руками в `psql`?
- Что делать, если миграция уже применена на сервере, а в ней ошибка?

## 6.6. API для сайтов: добавить, получить, удалить

**Что изучаем.** Ресурсный API: `POST /api/sites`, `GET /api/sites`,
`DELETE /api/sites/:id`. Слой доступа к данным отдельно от маршрутов.
Статусы `201`, `204`, `404`, `409`.

**Задание.** Реализовать API и отображение списка сайтов в клиенте с
добавлением и удалением.

**Критерии готовности.** Данные сохраняются после перезапуска сервера.

**Вопросы для самопроверки.**

- Какой статус вернуть при добавлении уже существующего URL?
- Где должна жить SQL-логика: в маршруте или отдельно? Почему?

## 6.7. Сохранение результатов проверок

**Что изучаем.** Запись истории: каждая проверка — новая строка. Время в БД
(`timestamptz`) и часовые пояса.

**Задание.** Сохранять результат каждой ручной проверки сайта и показывать
последний результат в списке.

**Критерии готовности.** После перезапуска виден последний результат каждого сайта.

**Вопросы для самопроверки.**

- Почему для времени лучше `timestamptz`, а не строка?
- Как получить последнюю проверку для каждого сайта одним запросом?

**Документация.**

- [PostgreSQL: Date/Time Types](https://www.postgresql.org/docs/current/datatype-datetime.html)

## 4.1. Запросы из браузера

**Что изучаем.** Браузерный `fetch` — тот же API, что в Node.js. Как увидеть
запросы во вкладке Network. `response.ok`, `response.status`, `response.json()`.

**Задание.**

1. Открыть клиент (`npm run dev` в `client`), в консоли DevTools выполнить
   `fetch` к любому публичному API и разобрать ответ.
2. Найти этот запрос во вкладке Network и посмотреть заголовки.
3. Попробовать из консоли обратиться к `http://127.0.0.1:3000/api/health` —
   записать, что произошло (разберём в следующей задаче).

**Критерии готовности.**

- Можете найти в Network любой запрос и прочитать его статус, заголовки, тело.

**Вопросы для самопроверки.**

- Почему `fetch` не бросает ошибку на ответ `404`?
- Почему `response.json()` тоже возвращает Promise?

**Документация.**

- [MDN: Using the Fetch API](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)
- [Chrome DevTools: Network](https://developer.chrome.com/docs/devtools/network)

## 4.2. CORS и прокси Vite

**Что изучаем.** Same-origin policy: браузер не даёт странице с одного
origin (схема + домен + порт) читать ответы с другого без разрешения сервера.
CORS — механизм такого разрешения через заголовки. Два решения для разработки:
разрешить CORS на сервере или проксировать `/api` через dev-сервер Vite,
чтобы для браузера всё было одним origin.

**Задание.**

1. Воспроизвести ошибку CORS и прочитать сообщение в консоли.
2. Разобрать, почему `curl` работает, а браузер — нет.
3. Настроить `server.proxy` в `client/vite.config.ts`, чтобы `/api` шёл на сервер.
4. Повторить запрос к `/api/health` (относительный путь) — убедиться, что работает.
5. Обсудить с наставником, почему выбран прокси, а не CORS на сервере, и что
   изменится в production (этап 9).

**Критерии готовности.**

- Из клиента запрос `fetch('/api/health')` успешен.
- Можете объяснить, кто именно блокирует запрос при ошибке CORS.

**Вопросы для самопроверки.**

- Что такое origin? Одинаковый ли origin у `localhost:5173` и `localhost:3000`?
- Доходит ли запрос до сервера при ошибке CORS?
- Защищает ли CORS сервер от запросов через `curl`?

**Документация.**

- [MDN: Same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy)
- [MDN: CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS)
- [Vite: server.proxy](https://vite.dev/config/server-options#server-proxy)

обработка отправки формы, `preventDefault`. Почему `<form>` лучше, чем
input + кнопка с `onClick`.

**Задание.**

1. Добавить в `App.tsx` форму с полем URL и кнопкой «Проверить».
2. Значение поля хранить в состоянии.
3. При отправке пока выводить введённый URL под формой.
4. Проверить, что отправка работает и по Enter.

**Критерии готовности.**

## 4.4. Запрос к API и отображение результата

**Что изучаем.** Отправка POST-запроса с JSON из браузера и отображение
результата. Где хранить типы ответа API на клиенте: дублировать или делить с
сервером — плюсы и минусы.

**Задание.**

1. При отправке формы вызывать `POST /api/check` с введённым URL.
2. Описать типы ответа на клиенте.
3. Отобразить результат: доступен ли сайт, статус, время ответа.
4. Обсудить варианты общих типов для клиента и сервера и выбрать один.

**Критерии готовности.**

**Вопросы для самопроверки.**

## 4.5. Состояния loading, error, success

**Что изучаем.** Интерфейс должен показывать, что происходит: идёт загрузка,
пришла ошибка или результат. Описание состояния UI через discriminated union
вместо набора независимых флагов (`isLoading`, `error`, `data`).

**Задание.**

1. Описать тип состояния запроса: `idle | loading | success | error`.
2. Во время проверки показывать индикатор и блокировать кнопку.
3. Ошибки показывать понятным сообщением.
4. Проверить на медленном сайте и с выключенным сервером.

**Критерии готовности.**

- Невозможно отправить повторный запрос, пока идёт текущий.
- Каждое из четырёх состояний видно в интерфейсе.

**Вопросы для самопроверки.**

- Почему набор флагов `isLoading` + `error` + `data` допускает невозможные состояния?
- Что произойдёт, если пользователь отправит две проверки подряд и ответы
  придут в обратном порядке?

**Документация.**

- [React: Reacting to Input with State](https://react.dev/learn/reacting-to-input-with-state)
- [React: Choosing the State Structure](https://react.dev/learn/choosing-the-state-structure)

## 4.6. Обработка ошибок и типизация ответов

**Что изучаем.** Виды ошибок на клиенте: сеть недоступна, сервер вернул
4xx/5xx, тело — не тот JSON, что ожидали. Вынос работы с API в отдельную
функцию с типизированным результатом.

**Задание.**

1. Вынести запрос в функцию `checkUrl(url): Promise<...>` в `client/src/api.ts`.
2. Обрабатывать: сетевую ошибку, ошибку валидации (`400` в формате из 3.7),
   непредвиденный ответ.
3. Проверить все случаи вручную (выключить сервер, ввести неверный URL).

**Критерии готовности.**

- Для каждого вида ошибки пользователь видит осмысленное сообщение.
- Компонент не знает деталей HTTP — только вызывает `checkUrl`.

**Вопросы для самопроверки.**

- Как отличить «сервер недоступен» от «сервер ответил ошибкой»?
- Зачем выносить работу с API из компонента?

**Документация.**

- [MDN: Checking that the fetch was successful](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch#checking_response_status)
